## 4. The secret path (PATH-01 in the server, PATH-02 in the web app, GO-10b in the helper)

**Today.** The site is served at the root of its address (`https://design.example.com/`).

**Change.** Every install serves the whole site under a random web base path, as xWriter does:
16 characters of `a-z` and `0-9` between slashes, for example `/k3v9x2m1q8wz7r4t/`. The site's
address becomes `https://design.example.com:34567/k3v9x2m1q8wz7r4t/` (the port, section 5).

- **Everything is under the path:** the pages, the API, the live editing socket (`live`), the
  MCP connector (`mcp`), uploaded media, downloads, the print page, view-only links and Claude
  links. Every link the site makes includes it: invite links, view-only links, Claude links,
  the Claude Code command on the Account page, the address on Settings > HTTPS.
- **Outside the path, an empty page (Q-35):** any other address on the site's port (the root,
  a wrong path) and every request on port 80 that is not a waiting Let's Encrypt check gets the
  same empty page: HTTP 404 with a
  tiny blank HTML document (`<!doctype html><title></title>`), because an empty 404 body makes
  Chrome show its own error page instead of an empty one. No header names xDesign. The path
  without its last slash (`/k3v9x2m1q8wz7r4t`) redirects to the path with it, as xWriter's gate
  does.
- **The app owns the path** (D-613): the app (`apps/server`) serves everything under its base
  path and answers the empty page outside it, so `make dev` and the server behave the same; the
  helper's front also answers the empty page itself for addresses outside the path, so nothing
  outside reaches the app. The session cookie's path is the base path.
- **The contract between the app and the helper:** `XD_BASE_PATH` (starts and ends with `/`,
  default `/`), and `XD_PUBLIC_URL`, which stays the origin with the port
  (`https://design.example.com:34567`); the app's own address for links is that origin plus the
  base path without its last slash (`https://design.example.com:34567/k3v9x2m1q8wz7r4t`), so
  code that adds `/v/<token>` to it keeps working. The helper's `serve` sets both from
  `config.toml`.
- **The page finds its path at run time:** the build is the same for every install; the app
  writes the base path into `index.html` when it sends it (xWriter writes its `<base href>`), and
  the web app builds every address from it: the router's base, API calls, the live socket,
  media, downloads.
- **Development:** `make dev` stays at http://localhost:5173/ (base `/`), so the owner's usual
  address keeps working; `make dev BASE_PATH=/k3v9x2m1q8wz7r4t/` runs the same site under a path
  to try it locally (D-613).
- **A path of `/`** is still possible (typed at the installer's question or given to
  `set-path`), with xWriter's warning: "with the web base path / anyone who finds the port finds
  the sign-in page; a random path is recommended".

## 5. Always a random port; xDesign serves HTTPS itself (GO-10a, GO-10b)

**Today.** Three HTTPS modes (07 section 4): A, xDesign serves HTTPS on 443 (ports free); B,
behind nginx, Caddy or Apache, which the installer configures with certbot; C, another port
(8443, else random) when a program xDesign cannot configure holds 443.

**Change (Q-33, D-609, replaces D-23's choice of modes).** One way only, today's mode C for
everyone: xDesign serves HTTPS itself on a random free port from 20000 to 60999 (xWriter's
range and code, already in `helper/internal/install/questions.go`), proposed at install and
changeable there. Ports 443 and 80 are left to other programs.

- **Certificates** work as mode C's do today (07 section 4.1 methods, Settings > HTTPS): with a
  domain and port 80 free, Let's Encrypt over port 80 (xDesign opens port 80 only while a check
  waits); port 80 held by another program: the built-in certificate with today's note pointing
  to "Let's Encrypt through Cloudflare DNS"; no domain: the IP address with the built-in
  certificate or Let's Encrypt for the IP address. Certificate files and a pasted certificate
  stay.
- **Port 80** answers only Let's Encrypt's checks while one waits; everything else gets the
  empty page. Today's redirect to the site's address is removed, because it would tell anyone
  the secret path (D-615).
- **Mode A and mode B are removed** from the installer, the helper, the website and the docs,
  since no site uses them (nothing is released yet, D-614): nginx, Caddy and Apache site files,
  certbot and its deploy hook, Caddy's import line, the SELinux boolean
  `httpd_can_network_connect`, the mode questions and the mode proposal, Settings > HTTPS's
  "HTTPS is handled by nginx on this server", and their uninstall steps.
  `/etc/xdesign/config.toml` loses `https_mode` and gains `base_path`; `listen` holds the port.
- **Kept:** the firewall step (it opens the site's port, and port 80 when xDesign answers Let's
  Encrypt there), the SELinux port label for the site's port, the provider-firewall hint in the
  end block with the actual port, adding a domain later in Settings > HTTPS (the port and path
  stay).
- **Everything the helper asks the app** (the install's and update's health checks, going back,
  `xdesign status`) uses the base path.

## 7. Moving the site later (GO-11)

Two root commands, as xWriter's `xwriter admin set-port` and `set-path` (Q-34, D-610):

- **`xdesign admin set-port PORT [--no-firewall] [--json] [--yes]`**: the port must be 1 to
  65535, not 80, and free ("port 8080 is in use; choose another one"). It shows the new
  address and asks ":: Move xDesign to port 40000? [Y/n]"; then opens the new port in the
  firewall first (unless `--no-firewall`; the rule to add by hand when no firewall tool is
  active), labels it under SELinux when enforcing, saves `config.toml`, restarts xDesign with the
  health check, and closes the old port if xDesign opened it. When the site does not come back,
  the old port is restored and nothing is left half-changed. The end: ":: xDesign now answers at
  https://design.example.com:40000/k3v9x2m1q8wz7r4t/".
- **`xdesign admin set-path PATH | --random [--json] [--yes]`**: the path is checked as at
  install. It warns before changing: "The old address stops working: view-only links and Claude
  links you already sent, and Claude Code's connection to xDesign, need the new address." and
  asks ":: Change the web base path? [y/N]"; then saves `config.toml`, restarts with the health
  check (going back on failure) and prints the new address.
- Both refuse while an update or a backup runs (the maintenance lock), are recorded in
  `install.json`'s history and the install log, and are listed in `xdesign --help` and 07
  section 7.
- No page of the website changes the port or path (the owner chose commands only).

## As built (M12)

**FLAG-01** (e176363), language flags. Every language shows its flag before its name in the 13
places of the plan, and also in the language chip of each problem in Checks (the uppercase code,
as in Compare), which the list did not name. The stylesheet has 85 rules: the 124 languages with a
flag use 85 distinct flags (English, American English and others share one). The flag is 1em high
and the globe 1.1em (xWriter's globe is a fixed 16 px), so both follow the size of the text beside
them, small in the chips and table headings. In the selects (Try it's language, Checks' filter) the
flag is in each item and in the shown value; "All languages" has none; the items' labels stay words
only. In the phone's button fields the tag is the flag and the code, a little wider than before (56
px). The cards' language line keeps its one-line truncation: a language that does not fit is cut
with the ellipsis. The rules are unlayered CSS, as xWriter's, so Tailwind width or display classes
do not change a flag. The generator is `apps/web/scripts/gen-flags.ts` (`make gen-flags`, a step of
`make gen`); `LanguageFlag` and `LanguageNames` are in `components/LanguagePicker.tsx`.

**PATH-01** (efb92d6), the server under the secret path. The server reads `XD_BASE_PATH` (default
`/`; `/` or 1 to 3 parts of 4 to 64 letters, digits, - or _ between slashes, as xWriter's
`CheckBasePath`) and keeps three values: `basePath`, `origin` (XD_PUBLIC_URL's origin: the Origin
check and the live upgrades' check) and `publicUrl` (origin plus the base path without its last
slash: invite, reset, view-only and Claude links, and the address on Settings > HTTPS). Fastify's
`rewriteUrl` takes the base path off every request before routing (`<base>api/health` is routed as
`/api/health`), so the routes of `packages/api` keep their root paths; a request outside the base
path is marked and goes on as `/`, so even an address Fastify cannot read gets the empty page
instead of Fastify's 400. The first onRequest hook answers marked requests before every other hook
(no security headers, no cookie): the base without its last slash, query kept, gets 308 to the
base; anything else gets the empty page (404, `text/html; charset=utf-8`,
`<!doctype html><title></title>`). Request logs show the path without the base; a request outside
it logs the address it asked for (view tokens still hidden). index.html is read once at start with
its `<base href="...">` replaced by the base path and sent by the SPA fallback for `<base>`,
`<base>index.html` and every client route, with @fastify/static's `cache-control: public,
max-age=0` (no ETag or Last-Modified any more); @fastify/static never sends index.html itself
(`allowedPath`). WebSocket upgrades are taken on `<base>live` only; any other upgrade gets the
empty page as its HTTP answer. The session cookie's Path is the base path.

**PATH-02** (ddb6446), the web app under the secret path. The web app takes its base from the
page: `basePath = new URL('.', document.baseURI).pathname` (`apps/web/src/lib/base.ts`; the folder
of the base, so it always ends with `/`). Every address it makes goes through that module:
`routeUrl` (and with it `call`, `mediaUrl`, uploads, downloads) adds the base in front of the
route's root path; the live socket is `socketUrl('/live')`; the Account page's MCP address is
`siteUrl('/mcp')`. TanStack Router gets `basepath: basePath`: route paths, `redirect`, `navigate`
and the locations the guards see stay without the base (`/sign-in`, `next=/d/abc`), and the router
adds it in the address bar, so the sign-in redirect and its way back needed no change. The Vite
plugin `xd:web-base-path` sets `base: './'` for the build and the dev base from `BASE_PATH`, writes
`<base href="BASE_PATH" />` into index.html in dev, and fails the build or the dev server when
index.html no longer has `<base href="/" />` exactly (the server replaces that text). It also
refuses a `BASE_PATH` that breaks the server's rule, so `make dev` stops at once instead of a
server waiting in watch mode. In dev, Vite itself answers addresses outside the base (its redirect
from `/` to the base, its 404 note elsewhere); only the server answers the empty page. Fonts (CSS
`url(./...)`), the Web Worker and lazy chunks are relative to their files; the preview's emoji
images are `./assets/emoji-<version>/` in the build, resolved against the `<base href>`. With a
`<base href>`, a bare `#fragment` link resolves against the base, so the shell's "Skip to content"
link moves the focus itself; the print page's in-page links already did.

**GO-10a** (b15bc72, 3311f37), one HTTPS way and the installer's port and path. Preflight checks
only port 80: " -> ports     80 free" or " -> ports     80 (nginx) in use". Port 443 is not
checked; the port question probes the port it gets. The installer proposes a random free port from
20000 to 60999 at ":: Site port [34567]:" and a random path of 16 characters of a-z and 0-9 at "::
Web base path [/k3v9x2m1q8wz7r4t/]:". With `--port` or `--base-path` the question proposes the
flag's value; `--yes` and `--dry-run` take them, else the random ones. A path of `/` (typed, or
`--base-path /`) prints "warning: with the web base path / anyone who finds the port finds the
sign-in page; a random path is recommended". `--port N` (1 to 65535, not 80, free) and
`--base-path PATH` (checked as `CheckBasePath`) replace `--https-port`; a port in use stops with
"--port N: the port is in use; choose another one". The summary's HTTPS line says the certificate

**GO-11** (2d544b8), `admin set-port` and `admin set-path`. `sudo xdesign admin set-port PORT
[--no-firewall] [--json] [--yes]` and `sudo xdesign admin set-path PATH | --random [--json]
[--yes]`; `--json` needs `--yes`. As another user: "xdesign admin set-port must run as root. Try:
sudo xdesign admin set-port 40000". A path without its slashes gets them ("abcd" is "/abcd/"), as
xWriter's set-path does. Steps of set-port: 1 New port, 2 Firewall, 3 SELinux network, 4 Settings,
5 Stop xDesign, 6 Start and health check, 7 Finish; going back: B1 Settings from before, B2 Start
xDesign on port 34567, B3 Close port 40000. set-path: 1 New web base path, 2 Settings, 3 Stop, 4
Start and health check, 5 Finish; going back B1 and B2. Each step is in the install log
(/var/log/xdesign-install.log) under "==== xdesign admin set-port 40000 ====". Step 1 shows " ->
port 34567 to 40000" (or " -> path /old/ to /new/") and " -> address
https://design.example.com:40000/k3v9x2m1q8wz7r4t/". It refuses "please give a port number from 1
to 65535", "port 80 cannot serve HTTPS; choose another one", "port 8080 is in use; choose another
one", "xDesign already uses port 34567", "xDesign already uses the web base path /x/", and an
invalid path with `CheckBasePath`'s text. The busy check (the maintenance lock) refuses while
xdesign-maintenance.service runs ("the server is busy with an update, a rollback, a restore, a
domain change or an address change asked for in the website (xdesign-maintenance.service runs): try again when it is
done") and while the backups' lock is held ("a backup is being made or restored now: try again
when it is done"); the commands take no lock of their own, so an update or rollback started by
hand in another terminal is not caught. set-port: an active ufw or firewalld that does not allow
the new port gets it opened in step 2 (no question; recorded in install.json's firewall ports, so
the uninstall closes it). With `--no-firewall` the note is "the firewall is left alone
(--no-firewall): allow TCP port 40000 in it yourself, for example: ufw allow 40000/tcp" (firewalld:
`firewall-cmd --permanent --add-port=40000/tcp && firewall-cmd --reload`); with no active ufw or
firewalld: "no active ufw or firewalld was found: if another firewall guards this server
(nftables, or your provider's), allow TCP port 40000 in it, for example: nft add rule inet filter
input tcp dport 40000 accept". set-port under enforcing SELinux asks the installer's question "::
Label port 40000 for HTTPS under SELinux (semanage port -a -t http_port_t -p tcp 40000)? [Y/n]"
before ":: Move xDesign to port 40000? [Y/n]"; the label is recorded in install.json as the
installer records it. The old port's label stays (recorded for the uninstall). A move across port
1024 (to or from 443, without port 80 for Let's Encrypt) rewrites xdesign.service with or without
`CAP_NET_BIND_SERVICE` and runs `systemctl daemon-reload`; going back puts the unit from before
back. After the health check on the new port, step 7 closes the old port when install.json says
xDesign opened it (with `--no-firewall` it notes "TCP port 34567 stays open in ufw
(--no-firewall)"), and records the run in install.json's history: `{"action": "set-port",
"version": "1.0.0", "change": "port 34567 to 40000"}` (set-path: `"change": "web base path /old/ to
/new/"`); a failed run is recorded with `"result": "rolled_back"` (went back) or `"failed"`. Going
back writes config.toml (and the unit) from before, restarts xDesign with its health check there,
then closes the new port and puts the new port's SELinux type back when this run changed them; a
failure of that last part is a warning with what to do by hand, and the record stays in
install.json. set-path warns (also with `--yes`) "The old address stops working: view-only links
and Claude links you already sent, and Claude Code's connection to xDesign, need the new address."
and, for `/`, the installer's warning about `/`; then asks ":: Change the web base path? [y/N]".
The end: ":: xDesign now answers at https://design.example.com:40000/k3v9x2m1q8wz7r4t/". A failure
prints "error: ..." with the log, then ":: Nothing was changed.", ":: xDesign went back to the port
34567 and answers at ... as before." or ":: Going back failed too. Send the log to the developer.".
`--json` prints `{status: changed|went_back|failed, from, to, address, notes, failed_step, log,
error}`. `xdesign --help` lists them in the admin line: "administration: reset-password <email>,
list-users, set-port PORT, set-path PATH | --random, maintenance --request". `backup.Running`
opens the backups' lock file read-only and never creates it, since run as root it made a
root-owned `.lock` that the xdesign user's daily backup could no longer open. A move is not a new
install: the history entries carry the running version and a `change` text, and Maintenance's kept
releases count only installs, repairs, updates and rollbacks.
