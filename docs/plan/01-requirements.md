# 01. Requirements

xDesign (codename `xdesign`) is a private website where the owner and the people they invite
design Telegram bots: every message the bot sends, every button with its look, and everything
that happens when a user presses a button, answers a question or does something else in the
chat. It is a design tool, not a bot builder: nobody writes code in it. The final export is the
exact design that a developer or Claude builds the real bot from.

Planned on 2026-11-23 from the owner's request and seven rounds of questions (section 3). Status:
planned, waiting for the owner's go (docs/status.md).

## 1. What xDesign is, in one page

- A website on the owner's own Linux server (Ubuntu, Debian or Fedora), reached over HTTPS on
  the owner's domain. Invite only: the owner invites people by link; everyone signs in with
  email and password.
- Each **bot design** is one Telegram bot. Every member can create designs and share their own
  with chosen people as **Editor**, **Commenter** or **Viewer**; the site owner sees and manages
  every design.
- Several people edit the same design **live together**, like Figma or Google Docs: changes and
  cursors appear instantly, nothing gets overwritten, and editing goes on offline and syncs when
  the connection is back.
- The editor is a **map of steps** (boxes with arrows: which button leads where) next to a
  **live phone that looks exactly like the Telegram app**: xWriter's Telegram preview, ported as
  it is, in its five looks (Web A, Web K, Desktop, Android, iOS), light and dark (Q-28). Click a
  box and edit it right on the phone: type the text, add buttons, pick their look. **Try it**
  lets you click through the bot like a real user, in the same exact look.
- It covers **every interaction a Telegram bot can have with a user in a private chat**, except
  Mini Apps (section 4, list agreed with the owner, Q-12).
- Button looks are only the ones Telegram really has: default, blue (primary), green (success),
  red (danger), plus an optional custom emoji icon (Bot API 9.4).
- Texts can have a version per language; right-to-left languages such as Persian show correctly.
- Logic is described in plain words with logic boxes: "If", "Question", "Remember", "Wait",
  "Developer step" (a job the developer does, with named outcomes), never with code.
- **Export**: one zip with the exact spec (JSON), a readable document (Markdown with a picture
  of every screen and a map of the flow) and a short guide for builders on how to read the spec.
  In stage 2, Claude or a developer's tool can also read a design straight from the website
  (a secret JSON link, and an MCP connector with personal keys).
- Built in **two stages**, each usable on its own (section 8).

## 4. Scope

### 4.1 In scope

Private chats between a bot and one user, everything a bot can do there through the Telegram
Bot API (9.4 and later), designed without code, plus the website around it (accounts, sharing,
live editing, comments, history, export, Claude link, install and update).

### 4.2 The interactions xDesign designs (owner's list, Q-12)

The catalog with Bot API names and limits is 08; the stage of each item is in section 8.

- **Messages the bot sends.** Text with formatting: bold, italic, underline, strikethrough,
  spoiler, inline code, code block, quote (and expandable quote), links, custom emoji. Photo,
  video, GIF (animation), audio, voice, round video (video note), file (document), sticker,
  album (media group), location, venue, contact. Poll, quiz, dice, checklist (see Q-26: only
  business-account bots can send checklists), paid media (Telegram Stars). Options: silent, no forwarding or saving (protected content), link preview
  options, message effect, caption above media, media spoiler, the "typing..." indicator, and a
  delay before sending.
- **Buttons.** Inline buttons: go to a step, open a link, copy text, pay, login link; each with
  its look (default, primary, success, danger) and an optional custom emoji icon. Bottom
  keyboard (reply keyboard): text buttons, share phone, share location, pick users, pick a group
  or channel, create a poll; one-time, always shown, hint text in the input field; removing the
  keyboard; force reply.
- **What a click does.** Edit the message, send a new one, delete it (and send a new one); a
  toast or an alert popup; open a link.
- **Asking the user.** Text, number, photo, video, file, voice, phone, location and more, with
  checks and what happens on a wrong answer.
- **Bot setup.** Commands menu (per language), menu button, bot name, short description
  ("about"), description (the "What can this bot do?" text), profile photo, start links
  (`t.me/yourbot?start=promo`).
- **Payments.** Telegram Stars invoices, subscriptions, refunds, card payments for physical
  goods with shipping options and receipts; sending a gift.
- **Other events.** The bot sets a reaction on a message; the user reacts to a bot message
  (see Q-27: Telegram may not report this in private chats);
  pinning and unpinning; messages the bot sends first (broadcasts, reminders after a delay);
  the user blocks or restarts the bot; a fallback for unexpected messages.

### 4.3 Out of scope (owner's answers)

- Mini Apps (Web Apps) and everything that only works inside them (Q-04).
- Groups, supergroups, forum topics and channels (Q-08).
- Inline mode (`@yourbot query` in any chat) and the buttons that open it (Q-08).
- Business-account bots, games, stories (not in the owner's list; they need groups, business
  accounts or a Mini App).
- Running a real bot, connecting to Telegram, or generating bot code. xDesign never talks to
  Telegram (D-11).
- Public sign-up (Q-05); interfaces in languages other than English (Q-18).

## 5. People and roles

- **Site owner**: created by the installer. Invites and removes people, resets passwords, sees,
  opens and manages every design (also ones not shared with them), runs Settings and Maintenance
  (backups, update).
- **Member**: an invited person. Creates their own designs (and becomes their design owner) and
  sees the designs shared with them.
- Per design (05 section 3):
  - **Design owner**: the member who created it (the site owner can transfer it). Everything an
    Editor can do, plus sharing, view-only links, Claude links, and deleting the design.
  - **Editor**: edits everything live, exports, comments, names versions, restores versions.
  - **Commenter**: sees everything, uses Try it, exports, writes comments; changes nothing.
  - **Viewer**: sees everything, uses Try it, exports; no comments, no changes.
- **Someone with a view-only link** (stage 2): no account; sees the map and the phone and uses
  Try it for that one design; nothing else.

## 6. Requirements by area

Each area has its own plan document; these are the owner-level requirements they implement.

### 6.1 Accounts and sharing (05)
1. Invite-only accounts with email and password; no mail server needed: invite and password
   reset links are copied and sent by the owner however they like.
2. Roles per design as in section 5; people see only what is shared with them.
3. A list of designs with search; create, rename, duplicate, delete (to a trash kept 30 days).

### 6.2 Live editing (05)
1. Everyone with edit rights edits at once; changes appear for all within about a second.
2. Avatars of who is in the design, their cursors on the map, and which box each person edits.
3. Undo and redo undo only your own changes.
4. Offline: keep editing when the connection drops; changes sync when it is back; the top bar
   says "Offline, your changes are kept on this computer".

### 6.3 The editor (04)
1. Map of steps with arrows, palette to add steps, live phone, Try it (Q-09).
2. Click a box: edit it on the phone (text, buttons, media); logic boxes get a clear form.
3. Auto-arrange, zoom, minimap, search on the map, copy and paste, duplicate a step.
4. Telegram look switch: xWriter's five looks in its order (Web A, Web K, Desktop, Android,
   iOS), light and dark, drawn exactly as xWriter draws them (Q-19, Q-28).
5. Limit checks while designing (Q-19), shown on the boxes and in a checks list.
6. The editor is made for a computer screen; viewing, comments and Try it work on phones (Q-21).

### 6.4 Content (03, 04, 08)
1. Every item of section 4.2, with exactly the options Telegram has.
2. Button looks: only default, primary, success, danger, plus a custom emoji icon (Q-03).
3. Media: upload real pictures and files (size limit, default 20 MB, owner can change) or a
   placeholder box with a description ("product photo") (Q-21).

### 6.5 Logic (03, 04)
1. Logic boxes in plain words: If, Question, Remember, Wait, Go to, End, Developer step, Note.
2. Saved answers and remembered values (variables) shown in texts as chips such as {name}.
3. Test-user switches (admin yes/no, paid yes/no, language, and any the designer adds) set the
   outcome of "If" boxes in Try it (Q-21).

### 6.6 Languages (03, 04)
1. A design has one or more languages and a default one; every text has a version per language.
2. Right-to-left languages show right to left in the phone, the editor and the export.
3. Missing translations are marked and listed; a translation table shows all texts side by side.

### 6.7 Try it (04)
1. Click through the bot on the phone like a real user, from any start point.
2. Questions take typed answers and check them; buttons do exactly what the design says
   (edit, new message, delete, popup).
3. At an "If" box the test-user switches decide, or Try it asks; at a "Developer step" you pick
   the outcome; "Wait" shows the wait and a "Skip the wait" button.
4. The path you take lights up on the map.

### 6.8 Export (06)
1. One zip: `spec.json` (exact), `design.md` (readable, with pictures and a Mermaid map),
   `HOW-TO-READ.md` (for builders), `bot-spec.schema.json`, the media files and the pictures.
2. The readable doc also opens as a printable page (save as PDF from the browser).
3. Every step and button has a short ID name (`main_menu`, `btn_shop`) made from its name and
   editable, used by the developer and Claude.
4. Import an xDesign zip or spec as a new design (moving designs between servers, backups).

### 6.9 Comments, history, view-only link, Claude link (stage 2; 05, 06)
1. Comments on a step or a button, with replies, resolve, and a notifications bell.
2. Version history: automatic versions while people edit, named versions, view, compare,
   restore, export a version.
3. View-only link: open without an account, see and click through, no changes; revocable,
   optional expiry.
4. Claude link: a secret JSON link per design (latest or a version), and an MCP connector with
   personal keys that lists and reads the designs a person can see. Both read-only.

### 6.10 Templates and reusable parts (Q-19)
1. Reusable parts (stage 1): a button row or a text made once and used on many steps; edit it
   once, it changes everywhere; detach to make a local copy.
2. Starter templates (stage 2): shop (with Stars payments), support desk, quiz, sign-up form;
   save any design as a template.

### 6.11 Server, install, backups and update (07)
1. Ships as one self-installing file like xWriter (the Go helper with the website inside,
   copied from xWriter and xmtp-panel, Q-29) and installs on Ubuntu, Debian or Fedora with one
   command, the same way as xWriter and xmtp-panel (Q-25).
2. HTTPS: on a free server xDesign gets and renews its own Let's Encrypt certificate; next to
   another web server it fits in on its own domain (Q-23).
3. One SQLite database file, daily automatic backups (14 kept) and a "Download backup" button.
4. Update by `xdesign update FILE` or by uploading the file in Maintenance: checks, a backup
   first, migrations, a health check, and going back by itself when the new version fails.

### 6.12 Defaults the owner accepted (Q-21)
- Export: one zip with `spec.json`, the readable doc with a picture of every screen, and a short
  "how to read this spec" guide; the readable doc also prints; every step and button has an ID
  name made from its name and editable.
- Claude link: an MCP connector and a plain JSON link, both with keys that can be revoked.
- Media: upload real files (size limit) or a placeholder with a description.
- Try it: the tester picks outcomes of "If" boxes and developer steps; test-user switches set
  them for the whole run.
- Devices: viewing, comments and Try it work on phones; the editor is for a computer screen.
- Server: one SQLite file, daily backups plus "Download backup"; the installer asks for the
  domain and sets up HTTPS itself; offline editing syncs later.
- Organizing: a list of designs with search; duplicate a design or a step in one click.

## 7. Quality requirements

1. **Easy for non-coders.** Plain words everywhere ("step", "button", "goes to"), never Bot API
   names in the main interface; Bot API names appear only in the export and in a "Telegram
   details" fold-out for the curious.
2. **Exact.** Everything the export says can be built with the Telegram Bot API exactly as
   drawn; things Telegram cannot do cannot be designed, or are flagged by a check.
3. **Fast.** A design with 300 steps opens in under 3 seconds and stays smooth to drag and zoom
   on an ordinary laptop.
4. **Safe.** Internet-facing but invite-only; passwords hashed with argon2id; secret links long
   and revocable; uploads checked; no third-party services; no telemetry.
5. **No data loss.** Every change is saved on the server within a few seconds and in the
   browser; daily backups; a backup before every update.
6. **One service.** One file `xdesign` (the Go helper with the Node app inside), one systemd
   service, one SQLite file and one data folder; no Redis, no separate database server, no
   Docker needed.

## 8. Stages (Q-17)

Each stage ends with a release the owner installs and uses.

- **Stage 1 (M1 to M6):** the website (install, update, backups, accounts, invites, roles,
  design list), live editing, the map, the phone with the look switch, Try it, limit checks,
  reusable parts, export and import. Content: all message kinds except polls, quizzes, dice,
  checklists, paid media and invoices; all buttons and keyboards (the pay button arrives with
  payments); everything a click does; questions; logic boxes (If, Question, Remember, Wait,
  Go to, End, Developer step, Note); start points (/start, start links, commands, bottom
  keyboard text, fallback); bot setup; languages and right to left.
- **Stage 2 (M7 to M11):** polls, quizzes, dice, checklists, paid media; payments (Stars,
  subscriptions, refunds, card payments with shipping); sending a gift; other events (reactions
  both ways, pins, the user blocks or restarts the bot, broadcasts, reminders); comments;
  version history; view-only link; Claude link (JSON link and MCP) with the picture cache;
  starter templates; the Telegram catalog refresh.

## 9. Words used in xDesign (interface glossary)

| Word | Meaning |
|---|---|
| Design | One bot: its steps, texts, buttons, languages and setup. |
| Map | The canvas with all steps as boxes and arrows. |
| Step | One box on the map: a message, a question, or a logic box. |
| Message step | Something the bot sends: text, media, poll and so on, with its buttons. |
| Start point | Where a conversation starts: /start, a start link, a command, a bottom-keyboard text, "anything else the user sends", and in stage 2 events such as a payment or a reaction. |
| Button look | Default, Blue (primary), Green (success), Red (danger). |
| Goes to | The arrow from a button or an outcome to the next step. |
| Show it by | How the next message appears after a click: "Edit this message", "Send a new message", "Delete this one and send a new one". |
| Popup | The small toast or the alert window Telegram shows after a click. |
| Saved answer / remembered value | A variable, shown in texts as a chip like {name}. |
| Developer step | A job only the developer can do (look up an order, check a code), with named outcomes. |
| Part | A reusable button row or text used on many steps. |
| Test user | The switches Try it uses for "If" boxes (admin, paid, language...). |
| Phone look | Web A, Web K, Desktop, Android or iOS (xWriter's five looks); light or dark. |
| Check | A warning or error about Telegram limits or a broken flow. |
| Spec | The exact export file (`spec.json`) builders build from. |

- `claude_optimized_xhigh.md` (in the project root) governs how the build runs: questions
  before plans, no code before the owner's go, Opus agents at effort xhigh for code, Sonnet only
  for lookups and documentation, short runs, briefs, `make sanity` as the only check.
- No em-dash (U+2014) anywhere: code, comments, texts, docs, commits.
- Git: author and committer `Sir-MmD <27060102+Sir-MmD@users.noreply.github.com>`; no Claude
  attribution anywhere; commit locally only; never push without the owner's word at that moment.
  The repository is `https://github.com/Sir-MmD/xdesign` (private), the remote `origin`.
- English interface texts exactly as written in the plan documents.
